## Project title

ContextMesh

## Project description

ContextMesh is a graph-native memory and coordination layer for multi-agent incident investigation, built on FalkorDB. When separate agent tasks or chat sessions start from zero, an investigation loses its earlier observations, ownership facts, and lessons from past incidents. ContextMesh stores sessions, user notes, evidence, entities, tasks, decisions, and agent handoffs as one FalkorDB graph per workspace, so later sessions retrieve them by traversing real relationships.

Four bounded runtime stages run over that graph. The Researcher retrieves matching memories and evidence, then expands along semantic relationships up to three hops. The Planner reads the Researcher's persisted output back from FalkorDB and creates dependent tasks. The Executor writes an evidence-backed Decision. The Verifier re-queries the paths, flags narrow contradictions (competing owner or current-TTL assertions), and states the evidence gaps. Every answer shows the supporting nodes and the actual `nodes(p)` / `relationships(p)` paths that FalkorDB returned. Paths are never generated by a language model.

The target users are engineering and operations teams who need agents whose reasoning can be inspected and continued across sessions. The React / TypeScript / Three.js UI shows the same persisted graph in 3D, with an accessible list view as an alternative.

What has been verified locally against a real FalkorDB v4.14.11 instance: a second session recalls a unique observation, its owner (Maya Chen), the Redis TTL change, and the earlier INC-104 lesson; results survive a browser refresh; results survive a restart of the FalkorDB and backend containers (`scripts/verify_demo.py --restart`); workspaces are isolated; and 17 automated tests pass. AcmeShop is a fully synthetic scenario. The app runs in deterministic demo mode without an LLM key. Groq synthesis is optional.

## Tracks

- **Agent Memory and Coordination** (primary). Persistent cross-session memory, and `HANDOFF_TO`-linked AgentRun records that downstream stages must read from the graph. A missing handoff stops the workflow, and a test covers this.
- **Agents That Act on Connected Data** (secondary). Agents retrieve and decide by traversing typed relationships (`OWNED_BY`, `AFFECTS`, `RESOLVED_BY`, `SUPPORTS`, `DEPENDS_ON`). The Executor's actions are limited to internal graph records; it does not operate external systems.
- *Company Brain*: not recommended. There is no multi-source enterprise ingestion and no authenticated organization-wide knowledge base.

## How FalkorDB was used technically

- **One graph per workspace.** The graph key is `contextmesh_<workspace_id>`, derived from a validated identifier. Queries never cross graphs. `test_workspace_isolation_and_injection` and `test_memory_revision_paths_and_neighborhood_are_workspace_local` verify this.
- **Typed schema.** Node kinds are Workspace, Session, Memory, Evidence, Entity, Task, Decision, Agent, AgentRun, and Run. Relationships are `HAS_SESSION`, `HAS_MEMORY`, `HAS_RUN`, `MENTIONS`, `RELATES_TO`, `SUPPORTS`, `DEPENDS_ON`, `GENERATED`, `HANDOFF_TO`, `OWNED_BY`, `AFFECTS`, `RESOLVED_BY`, and `NEXT`. Labels and relationship types come from fixed allowlists. All values are Cypher parameters, and no endpoint accepts Cypher.
- **Multi-hop retrieval.** Term-matched anchors (at most 12) are expanded with `MATCH p=(s)-[:MENTIONS|RELATES_TO|SUPPORTS|DEPENDS_ON|OWNED_BY|AFFECTS|RESOLVED_BY*1..3]-(n) WHERE s.id IN $ids RETURN [x IN nodes(p) | x.id], [r IN relationships(p) | type(r)]`. Session and run hubs are excluded from this expansion. Paths whose nodes fall outside the returned context are dropped, so every displayed path is backed by edges that were actually returned.
- **Persisted handoffs.** Each stage writes an AgentRun node, and consecutive stages are linked with `HANDOFF_TO`. The next stage reloads that record from FalkorDB rather than taking it in memory. `test_missing_persisted_handoff_prevents_downstream_work` verifies this.
- **Provenance.** User notes are stored with `trusted: false`. A memory revision first writes the previous text as an Evidence node. Earlier Decisions are excluded from later evidence, so the system does not treat its own conclusions as independent sources.
- **Durability.** FalkorDB runs with AOF on a named Docker volume. The restart test re-reads a completed run after both containers restart.
